# iOS Super App Template — Project Rules (System Instructions)

You are an expert iOS / Swift engineer. When working in this repository, adhere
strictly to the standards below. The authoritative reference is
**`docs/architecture/ARCHITECTURE.md`** (written in Task 9); this file is the
short form.

## Architecture & design (Feature-First Clean Architecture)

- **Dependency rule**: `Presentation → Domain ← Data`.
  - `Presentation` MUST NOT reference `Data` directly.
  - `Domain` MUST NOT import anything from `Presentation` or `Data`.
  - `Domain` MUST be **pure Swift** — no `SwiftUI` / `UIKit` / `Combine`, no
    platform types.
- **Unidirectional data flow**: `View → ViewModel → Domain → Data → Domain →
  ViewModel → View`.
- **Package per module**: every infrastructure module, the `Shell`, and every
  feature is its own local SPM package. Boundaries are enforced by the compiler
  (no declared dependency ⇒ no import), by `ArchTests` (K1–K9, swift-syntax),
  and by `scripts/check_module_boundaries.sh`.
- **Features never depend on features.** Cross-feature communication goes
  through `Platform` — `AppRoutes` (shared route registry) and `AppEventBus`.
  A temporary exception must be listed in
  `scripts/module_boundary_whitelist.txt` (empty by default).
- **Composition happens only in `App/`.** The host is the one place that knows
  about more than one feature; it wires DI and registers each feature's
  `RouteProvider`. `Shell` is feature-blind.

## Presentation layer (MVI)

- **State** (`ViewModel → View`): the persistent UI snapshot. Published from the
  `ViewModel`; the `View` observes it.
- **Action** (`View → ViewModel`): user input. One entry point —
  `dispatch(_:)` → `onAction(_:)`. No other public mutation surface.
- **Event** (`ViewModel → View`): one-shot side effects (navigation, alerts).
- **Async effects**: a running effect `Task` is stored and cancelled when a new
  action supersedes it (Source Spec §5.5).
- **Dumb views**: SwiftUI views take `State` in and emit `Action` out — no
  business logic.

## Domain layer

- **UseCases**: one business operation per `*UseCase` type (single
  responsibility).
- **Entities**: plain Swift value types — no persistence / serialization
  annotations.
- **Repository protocols** are declared in `Domain`; implementations live in
  `Data`.

## Data layer

- **`*RepositoryImpl`** implements the `Domain` protocol and coordinates remote
  + local sources.
- **All types in `Sources/*/Data/` are `internal`** — never `public` / `open`.
- **DTOs** are separate from entities; mapping is explicit.
- Model async results with an explicit `Result`-like type, not `throws`
  crossing layer boundaries.

## Project structure & build

- **Tuist manifests are the source of truth.** `.xcodeproj` / `.xcworkspace`
  are generated by `tuist generate` and git-ignored — never hand-edit a
  `.pbxproj`.
- **No hard-coded versions.** Tool versions live in `.mise.toml` /
  `.tuist-version`; the deployment target lives once in
  `Tuist/ProjectDescriptionHelpers/Module.swift`.
- **Marker regions** (`// tuist:packages:begin/end`, `// tuist:app-deps:*`,
  `// app:route-providers:*`) are edited by Mason bricks — keep them verbatim.
- **Quality gates run from the repo root**: `swiftlint --strict --config
  quality/.swiftlint.yml` and `swiftformat --config quality/.swiftformat .
  --lint` (the configs use `../`-relative paths).

## Naming conventions

| Concept | Name | Location |
|---|---|---|
| Contract triplet | `[Feature]Action` / `[Feature]State` / `[Feature]Event` | `Presentation` |
| View model | `[Feature]ViewModel : MviViewModel` | `Presentation` |
| Use case | `[Verb][Noun]UseCase` (e.g. `LoadSettingsUseCase`) | `Domain` |
| Repository | `[Noun]Repository` (protocol) / `[Noun]RepositoryImpl` | `Domain` / `Data` |
| Screen | `[Feature]View : View` | `Presentation` |
| Route provider | `[Feature]RouteProvider : RouteProvider` | `Presentation` |

## Working rules

- **One commit per task.** No unrelated changes; never commit the generated
  Xcode project.
- **No product domain** in shared code — the template is domain-neutral; the
  sample features are illustrative.
- **Tests**: match the tier the task declares (Source Spec §9A). Tier A is
  RED-before-GREEN with boundary-value + equivalence-partition scenarios.
